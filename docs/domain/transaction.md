# Transactions

## 1. Purpose

A transaction represents a financial operation affecting a wallet.

Transactions describe the movements and operations that explain how a wallet's holdings and cash position evolve over time.

They are user-provided business data. Patrimonia validates and enriches these transactions before using them to calculate wallet balances.

A transaction is an operation, not necessarily a single movement on one asset. Some operations involve multiple movements, represented by related transactions.

## 2. Transaction types

Patrimonia supports the following transaction actions:

| Action | Description |
|---|---|
| `cash_in` | Cash contribution to a wallet |
| `cash_out` | Cash withdrawal from a wallet |
| `buy` | Purchase of a financial asset |
| `sell` | Sale of a financial asset |
| `yield` | Income generated by an asset, such as interest or dividends |
| `fees` | Fees charged to the wallet or an operation |
| `gift` | Asset received without a purchase |

The action determines how the transaction affects the wallet's positions and investment amounts.

### 2.1 Cash movements

`cash_in` and `cash_out` represent contributions to and withdrawals from a wallet.

They apply to the wallet's cash asset (`cash_asset`).

The cumulative net investment is calculated as:

\[
\text{Net Investment} =
\sum \text{cash\_in} - \sum \text{cash\_out}
\]

This represents the net amount contributed by the user, independently of the wallet's market performance.

### 2.2 Asset purchases and sales

`buy` represents the acquisition of an asset.

`sell` represents the disposal of an asset.

These operations affect the quantity held in the corresponding asset position.

Purchases and sales may also generate associated cash movements. When such counterpart transactions are required, they are represented explicitly and linked to the originating operation.

### 2.3 Income, fees and gifts

`yield` represents income received from an asset, such as interest or dividends.

`fees` represents costs charged to the wallet or to an investment operation.

`gift` represents an asset received without a purchase. It increases the quantity held without representing an additional cash investment.

For these actions, the transaction quantity is zero (`qty = 0`). The financial amount is recorded separately.

## 3. Transaction attributes

A transaction contains the information needed to identify and interpret a financial operation.

| Attribute | Description |
|---|---|
| `date` | Date of the operation |
| `action` | Transaction type |
| `asset_id` | Identifier of the affected asset, when applicable |
| `asset_name` | Human-readable asset name |
| `qty` | Quantity involved in the operation |
| `price` | Unit price |
| `value` | Total financial value of the operation |

The exact required and optional attributes depend on the transaction action and are defined by the transaction data schema.

### 3.1 Source attributes and enriched attributes

Patrimonia distinguishes between user-provided transaction information and values calculated during enrichment.

The source data describes the original operation. Enriched data may include additional calculated attributes, such as:

- `pru_shares`: the unit cost basis associated with the position;
- `pru_value`: the total cost basis associated with the transaction or remaining position, according to the enrichment model.

These calculated attributes are not independent sources of truth. They are regenerated from validated source transactions and the relevant preceding wallet state.

## 4. Transaction relationships

Some financial operations involve more than one asset or movement.

For example, purchasing an investment asset may involve:
- an acquisition of the investment asset;
- a corresponding cash outflow.

When a cash counterpart is required, Patrimonia represents it as a separate transaction associated with the originating operation.

The relationship between the original transaction and its counterpart must be explicit and unambiguous.

A valid pair must satisfy the following conditions:

- the counterpart is unique;
- it refers to an existing originating operation;
- both transactions have the same operation date;
- their financial amounts are consistent;
- their ordering is valid for the operation being represented.

These constraints ensure that an operation is not counted twice or represented inconsistently.

## 5. Validation rules

Transactions must be validated before they can be used in enrichment or balance calculations.

Validation covers both individual transactions and relationships between transactions.

### 5.1 Individual transaction validation

Validation checks include:

- supported action;
- valid operation date;
- valid asset reference when required;
- valid quantity and financial values;
- action-specific constraints;
- consistency between quantity, unit price and operation value where applicable.

For example:
- `cash_in` and `cash_out` must concern the wallet's cash asset;
- `yield`, `fees` and `gift` require a zero quantity;
- a transaction must not refer to an unknown asset.

The detailed structural and business constraints are defined in the transaction schema and business rules.

### 5.2 Position constraints

Transactions must not produce invalid wallet positions.

In particular:
- a sale must not exceed the available quantity of the asset;
- a cash withdrawal must not exceed the available cash position;
- transactions must be processed in chronological order when calculating position changes.

These checks depend on the wallet's preceding state and cannot always be performed by validating an isolated transaction.

### 5.3 Pair validation

When an operation requires a cash counterpart, validation must ensure that the pair is complete and consistent.

An incomplete or inconsistent pair makes the affected transaction data invalid for subsequent calculations.

## 6. Average cost basis (PRU)

Patrimonia uses a weighted average cost basis (*Prix de Revient Unitaire*, or PRU) to track the acquisition cost of an asset position.

The PRU represents the average acquisition cost per unit of the remaining position.

For a purchase, the position's cost basis is updated using the previous position and the new acquisition.

For a sale, the cost basis associated with the sold quantity is removed from the position. The remaining position retains its average unit cost, subject to the applicable transaction rules.

The general weighted average calculation is:

\[
PRU_{\text{new}} =
\frac{
Q_{\text{old}} \times PRU_{\text{old}}
+
Q_{\text{bought}} \times P_{\text{buy}}
}{
Q_{\text{old}} + Q_{\text{bought}}
}
\]

Where:
- \(Q_{\text{old}}\) is the quantity held before the purchase;
- \(PRU_{\text{old}}\) is the previous unit cost basis;
- \(Q_{\text{bought}}\) is the acquired quantity;
- \(P_{\text{buy}}\) is the acquisition unit price.

The PRU calculation must account for the initial position when a preceding official balance is available.

The enrichment process calculates the PRU from validated source transactions and the relevant initial wallet state. The resulting enriched transactions are then used by balance calculations.

## 7. Transaction enrichment

Transaction enrichment transforms validated source transactions into a normalized and calculation-ready representation.

The process:
1. Loads the user's source transactions.
2. Validates their structure and business constraints.
3. Resolves transaction relationships and required cash counterparts.
4. Processes transactions in chronological order.
5. Calculates derived attributes, including the PRU information.
6. Produces the enriched transaction dataset.

The enriched dataset is a calculated result, not a user-maintained source.

It is fully regenerated from validated source data whenever a calculation command triggers the enrichment process. A previous enriched result is not used as the basis for the next calculation.

This guarantees that the enriched dataset remains consistent with the current validated inputs.

## 8. Role in balance calculation

Enriched transactions provide the transaction history used to calculate wallet balances.

A balance calculation combines:
- the latest applicable official balance;
- enriched transactions occurring after that balance's date;
- the requested calculation date.

Only transactions up to the requested date are taken into account.

The enriched transaction dataset therefore acts as an intermediate calculation result between user-provided transaction data and calculated wallet balances.

## 9. Data ownership and lifecycle

Transaction data follows three distinct stages:

| Stage | Ownership | Purpose |
|---|---|---|
| Source transactions | User | Original financial operations |
| Enriched transactions | Patrimonia | Validated and calculated transaction representation |
| Calculated balances | Patrimonia | Wallet positions derived from the official balance and transactions |

Patrimonia never modifies the user's original transaction files.

Enriched transactions are regenerated when needed and can be recreated from the validated source data.

For storage formats, file organization and configuration, see [User and Wallet Data](../data/users-wallets.md).
