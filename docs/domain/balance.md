# Wallet Balances

## 1. Purpose

A wallet balance represents the financial position of a wallet at a given date.

It provides a snapshot of the assets and cash held in the wallet. It is used as a reference point for tracking portfolio evolution and calculating subsequent balances.

Patrimonia distinguishes between two types of balances:

- **Official balances**: reference data supplied or explicitly approved by the user.
- **Calculated balances**: balances generated by Patrimonia from an official balance and subsequent enriched transactions.

These two types have different roles and must not be confused.

## 2. Balance contents

A balance describes the positions held in a wallet at a specific date.

A position represents the holding of a particular asset and includes the information required to describe its quantity and financial value.

Typical position attributes include:

| Attribute | Description |
|---|---|
| `asset_id` | Identifier of the asset |
| `asset_name` | Human-readable asset name |
| `qty` | Quantity held |
| `value` | Financial value of the position |

The exact attributes and validation constraints are defined by the balance data schema.

A balance also contains metadata identifying the wallet, the balance date and its provenance.

## 3. Official balances

An official balance is a reference snapshot provided or explicitly approved by the user.

It may originate from:
- a statement or valuation supplied by the financial institution;
- a balance previously calculated by Patrimonia and subsequently copied into the user's input data.

In both cases, the user explicitly decides to make the balance an official reference.

### 3.1 Provenance

The provenance identifies the origin of an official balance:

| Provenance | Meaning |
|---|---|
| `broker` | Balance originating from the financial institution |
| `patrimonia` | Balance previously calculated by Patrimonia and explicitly adopted by the user |

Provenance describes the origin of the data. It does not determine whether the balance is authoritative: an official balance is authoritative because the user has explicitly selected it as a reference.

### 3.2 Ownership and immutability

Official balances belong to the user's input data.

Patrimonia may read and validate them, but must never modify them automatically.

If a user wants to replace an official balance, the user must update the corresponding input data explicitly.

## 4. Calculated balances

A calculated balance is a snapshot generated by Patrimonia for a requested date.

It is calculated from:
- the latest applicable official balance;
- enriched transactions occurring after that balance's date;
- the requested calculation date.

The calculation applies the relevant transactions chronologically to the initial positions.

Only transactions dated after the reference balance and up to the requested date are included.

### 4.1 Calculation principle

Let:

- \(B_0\) be the initial official balance;
- \(T\) be the set of applicable enriched transactions;
- \(D\) be the requested calculation date.

The calculated balance is conceptually:

\[
B(D) = B_0 + \operatorname{Apply}(T, B_0, D)
\]

Where `Apply` represents the application of the relevant transactions to the initial wallet positions.

This notation describes the calculation principle, not a simple arithmetic addition of transaction values. Each transaction affects the relevant asset position according to its action and business rules.

### 4.2 Valuation

A calculated balance must represent the wallet's positions at the requested date.

When market valuation is required, Patrimonia uses the applicable asset quote available on or before that date.

For assets configured with `quote_always_one: true`, the unit value is always one.

The valuation rules depend on the asset type and its quote configuration.

### 4.3 Regeneration

Calculated balances are derived data.

They can be regenerated from the official balance, validated source transactions, enriched transactions and applicable quote data.

They are not used as an automatic replacement for official balances.

## 5. Official and calculated balance lifecycle

The relationship between the two balance types is explicit:

1. The user provides an official balance.
2. Patrimonia validates the official balance.
3. Patrimonia enriches the wallet's source transactions.
4. Patrimonia calculates a balance for the requested date.
5. The calculated balance is stored as derived data.
6. If the user wants to use this result as a new reference, the user explicitly copies it into the official input data.

This process prevents calculated results from silently becoming new reference data.

A calculated balance with `patrimonia` provenance does not become official merely because Patrimonia generated it.

## 6. Validation rules

Balances must be validated before they can be used as calculation inputs or outputs.

Validation covers both structural correctness and business consistency.

### 6.1 Structural validation

Structural validation checks include:

- valid wallet identification;
- valid balance date;
- valid provenance where applicable;
- valid asset references;
- valid position quantities and values;
- absence of duplicate positions for the same asset, where the data model requires uniqueness.

The detailed constraints are defined in the balance schema and associated business rules.

### 6.2 Business validation

Business validation checks include:

- all referenced assets exist;
- quantities and values are consistent with the asset's characteristics;
- the balance belongs to the expected wallet;
- the balance can serve as a valid reference for the requested calculation.

A balance must not be used as a calculation reference if its validation fails.

### 6.3 Calculation prerequisites

Before calculating a balance, Patrimonia must ensure that:

- an applicable official balance is available;
- the official balance is valid;
- the required transaction enrichment has completed successfully;
- the enriched transactions contain no blocking validation errors;
- the data required for valuation is available.

If these prerequisites are not met, the calculation must fail with an explicit error rather than produce an unreliable result.

## 7. Relationship with transactions

Transactions describe operations that change wallet positions over time.

A balance describes the resulting positions at a particular date.

The two concepts are complementary:

| Concept | Role |
|---|---|
| Transaction | Describes a financial operation |
| Official balance | Establishes a reference position |
| Enriched transaction | Provides validated and calculated transaction data |
| Calculated balance | Represents positions after applying relevant transactions |

The official balance provides the starting point for calculating subsequent positions. Enriched transactions explain the changes since that reference date.

See [Transactions](transaction.md) for transaction types, relationships, validation and enrichment rules.

## 8. Data ownership and storage

Balance data follows two distinct ownership models:

| Balance type | Storage area | Owner | Modified by Patrimonia |
|---|---|---|---|
| Official balance | User input data | User | No |
| Calculated balance | Calculated data | Patrimonia | Yes, through regeneration |

The physical formats, directory structure and configuration are documented in [User and Wallet Data](../data/users-wallets.md).

The separation between input and calculated data ensures that user-approved reference information is preserved while derived results remain reproducible.
