# Data Flow

## 1. Purpose

This document describes how data moves through Patrimonia, from its original sources to the results produced by the application.

It complements the architecture overview by focusing on data transformations, validation boundaries, persistence, and dependencies between processing steps.

The main objectives are to:

- Preserve the integrity of original data.
- Make data transformations explicit.
- Separate user-provided data from application-generated results.
- Ensure that calculated data can be regenerated from validated sources.
- Provide sufficient traceability to understand where results come from.

## 2. Data Domains

Patrimonia organizes its data into three main domains.

| Domain | Location | Responsibility |
|---|---|---|
| Reference data | `data/` | Shared reference information maintained by Patrimonia administrators. |
| User input data | `external-data/.../input/` | Original data provided or validated by users. |
| Calculated data | `external-data/.../calculated/` | Results generated by Patrimonia from validated sources. |

These domains have different ownership and lifecycle rules.

### 2.1 Reference Data

Reference data describes financial instruments, account contracts, categories, and other shared information.

It is maintained separately from individual user data.

Some reference data can be enriched using external providers through the asset `fetch` and `apply` workflows.

### 2.2 User Input Data

User input data contains information explicitly provided or validated by users.

Examples include:

- Transaction workbooks.
- Official balance workbooks.
- User and wallet configuration files.

Patrimonia reads and validates these files but does not modify them.

An input file remains the original source, even when it contains information previously generated by Patrimonia and subsequently copied into the input directory by the user.

### 2.3 Calculated Data

Calculated data contains results generated by Patrimonia.

Examples include:

- Enriched transactions.
- Calculated balances.
- Historical portfolio values.
- Dashboard files and their metadata.

Calculated data is not an independent source of truth. It is derived from reference data, user input data, and the applicable calculation logic.

Whenever a calculation is triggered, its output should be regenerated from the relevant validated sources rather than relying on a previous calculated result as an input.

## 3. General Data Processing Flow

The general processing sequence is:

1. Load the required configuration and reference data.
2. Read the relevant user input data.
3. Validate the input data.
4. Transform validated data into application models.
5. Execute the required business calculations.
6. Validate the resulting data where applicable.
7. Persist the calculated output.
8. Record relevant metadata for traceability.

The application separates these responsibilities:

- **Repositories** handle data access, validation, and persistence.
- **Adapters** handle external providers and format-specific operations.
- **Models** represent application and domain data independently of storage formats.
- **Services** orchestrate processing and business operations.
- **Bootstrap** assembles the components and injects their dependencies.

Services do not directly manipulate YAML or Excel files.

## 4. Reference Asset Data Flow

Reference assets can be enriched with information obtained from external providers.

The workflow consists of two distinct operations: `fetch` and `apply`.

### 4.1 Fetch

The fetch operation retrieves external information and stores it as scraped data.

```text
Reference Asset
      |
      v
Asset Repository
      |
      v
Asset Service
      |
      v
Provider Adapter
      |
      v
External Provider
      |
      v
Scraped Data
      |
      v
Validation
      |
      v
Scraped Data Repository
      |
      v
Persisted Scraped Data
```

The main steps are:

1. Load the existing asset.
2. Identify the relevant provider and provider-specific identifier.
3. Retrieve the external information through the appropriate adapter.
4. Build the scraped data representation.
5. Validate the scraped data.
6. Persist it if it is valid and satisfies the applicable freshness rules.

Fetching data does not modify the reference asset itself.

### 4.2 Apply

The apply operation transforms validated scraped data into an updated reference asset.

```text
Reference Asset -----------+
                           |
                           v
                    Asset Service
                           ^
                           |
Scraped Data --------------+
      |
      v
Scraped Data Validation
      |
      v
Transformation
(scraped_to_catalog)
      |
      v
Final Asset Validation
      |
      v
Asset Repository
      |
      v
Updated Reference Asset
```

The main steps are:

1. Load the existing reference asset.
2. Load the corresponding scraped data.
3. Validate the scraped data.
4. Transform the scraped representation into the reference asset representation.
5. Validate the resulting asset.
6. Persist the updated asset.

The reference catalogue is modified only during the apply operation.

### 4.3 Refresh

The refresh operation orchestrates both steps:

```text
Refresh
   |
   +--> Fetch
   |
   +--> Apply
```

This separation makes it possible to inspect and validate retrieved information before applying it to the shared reference catalogue.

## 5. Transaction Data Flow

Transactions are initially provided by users through Excel workbooks.

Patrimonia validates these source files and generates an enriched YAML representation.

The enriched transactions are then used as the basis for balance calculations.

### 5.1 Transaction Input

Transaction workbooks are stored under the user's input directory:

```text
external-data/
└── users/
    └── <USER_ID>/
        └── input/
            └── <WALLET_ID>/
                └── transactions/
                    └── <YEAR>.xlsx
```

A transaction workbook contains:

- A `header` worksheet with metadata.
- A `data` worksheet containing transaction records.

The source workbook is user-managed and is never modified by Patrimonia.

### 5.2 Validation and Enrichment

The processing flow is:

```text
Transaction Excel Files
          |
          v
Transaction Repository
          |
          v
Excel Reader
          |
          v
Structural Validation
(JSON Schema)
          |
          v
Business Validation
          |
          v
Transaction Models
          |
          v
Transaction Enrichment
          |
          v
Enriched Transaction Models
          |
          v
YAML Persistence
          |
          v
Calculated Transactions
```

The process includes:

1. Reading the source workbooks.
2. Checking their structure and metadata.
3. Validating transaction records against the applicable schema.
4. Applying business validation rules.
5. Converting valid records into transaction models.
6. Enriching transactions with calculated information, including PRU-related values.
7. Persisting the enriched transactions in YAML format.

### 5.3 Full Recalculation

The enriched transaction dataset is fully regenerated whenever a command triggers its calculation.

The previous enriched output is not used as the basis for the new calculation.

Instead, Patrimonia reads the validated source transaction files and performs the complete enrichment process again.

```text
Validated Transaction Sources
             |
             v
      Full Recalculation
             |
             v
   Enriched Transaction Dataset
             |
             v
       YAML Persistence
```

This approach ensures that the calculated dataset reflects the current validated source files.

It also avoids the complexity of incremental updates and synchronization between source and calculated records.

The enriched transaction dataset is a derived result, not an additional source of truth.

## 6. Balance Data Flow

Patrimonia distinguishes two types of balances:

- Official balances, provided or explicitly validated by the user.
- Calculated balances, generated by Patrimonia.

These two types have different roles and storage locations.

### 6.1 Official Balances

Official balance workbooks are stored under:

```text
external-data/
└── users/
    └── <USER_ID>/
        └── input/
            └── <WALLET_ID>/
                └── balances/
                    └── <YEAR>.xlsx
```

They represent the reference balance information used by Patrimonia.

The source may originate from a financial institution or from a previous Patrimonia calculation that the user has explicitly chosen to adopt as an official input.

The `provenance` metadata identifies the origin of the balance, for example:

- `broker`
- `patrimonia`

The processing flow is:

```text
Official Balance Workbook
            |
            v
    Balance Repository
            |
            v
      Excel Reader
            |
            v
   Structural Validation
            |
            v
    Business Validation
            |
            v
      Balance Models
            |
            v
    Validated Official Balance
```

Official balance files are read-only from Patrimonia's perspective.

### 6.2 Calculated Balances

A calculated balance represents a wallet's estimated state at a user-selected date.

It is derived from:

- The latest applicable official balance.
- The enriched transactions occurring after that balance and up to the requested calculation date.
- The relevant reference data and calculation rules.

The processing flow is:

```text
Official Balance
       |
       |
       +--------------------------+
                                  |
                                  v
Enriched Transactions ---> Balance Calculation
                                  ^
                                  |
                         Reference Data
                                  |
                                  v
                         Calculated Balance
                                  |
                                  v
                         Validation
                                  |
                                  v
                         YAML / Excel Output
```

The calculated balance is persisted under the calculated data directory:

```text
external-data/
└── users/
    └── <USER_ID>/
        └── calculated/
            └── <WALLET_ID>/
                └── balances/
```

The calculation date determines the transaction cutoff.

Only transactions relevant to the period between the reference balance and the requested date are taken into account.

The exact calculation rules, including the treatment of transaction types and asset valuation, are defined by the corresponding business logic.

### 6.3 Official Adoption of a Calculated Balance

A calculated balance does not automatically become an official balance.

If a user wants to use a Patrimonia-generated balance as a new reference, the user must explicitly copy or export it into the input directory.

```text
Calculated Balance
        |
        | Explicit user action
        v
Official Balance Input
        |
        v
New Reference for Future Calculations
```

This explicit step preserves the distinction between application-generated results and user-approved reference data.

## 7. Portfolio Evolution Data Flow

Patrimonia can generate historical portfolio value data at two levels:

- Individual wallet.
- Consolidated user portfolio.

Evolution data consists of daily portfolio values without detailed position-level information.

The data is derived from the relevant balance and valuation information.

It is stored in YAML files organized by year:

```text
external-data/
└── users/
    └── <USER_ID>/
        └── calculated/
            └── ...
                └── evolution/
                    ├── <YEAR>.yaml
                    └── ...
```

Each yearly file contains:

- A header with generation metadata.
- A data section containing daily values.

The data is calculated output and can be regenerated when required.

## 8. Dashboard Data Flow

Dashboards are static HTML documents generated from calculated portfolio data.

Plotly is used to generate the visualizations.

The general flow is:

```text
Calculated Portfolio Data
            |
            v
      Dashboard Service
            |
            v
       Data Preparation
            |
            v
      Plotly Visualization
            |
            v
        HTML Dashboard
            |
            +----> Dashboard Metadata YAML
```

The dashboard HTML is accompanied by a YAML metadata file.

For example:

```text
<WALLET_ID>_dashboard.html
<WALLET_ID>_dashboard.meta.yaml
```

The metadata records relevant information about the generated dashboard, such as:

- Generation timestamp.
- Calculation date, when applicable.
- Scope.
- Wallet or user identifier.
- Generator application and version.
- Source references and semantic hashes.
- Result role.

The metadata helps identify the data used to produce the dashboard and understand its generation context.

## 9. Validation Boundaries

Validation is performed at several points in the data flow.

| Data | Validation responsibility |
|---|---|
| User transaction workbooks | Structural and business validation before enrichment. |
| User official balance workbooks | Structural and business validation before use. |
| Scraped provider data | Validation before persistence and application. |
| Updated reference assets | Validation before catalogue persistence. |
| Calculated results | Validation where applicable before persistence. |

Validation prevents malformed or inconsistent data from silently propagating into subsequent calculations.

A failed validation must prevent the affected invalid data from being used in a newly generated result.

Error messages should identify the source file and, where possible, the relevant worksheet, row, field, and validation rule.

## 10. Traceability and Data Integrity

Calculated data should contain enough metadata to identify its origin.

A common metadata model is used as a basis for calculated outputs, with fields adapted to each result type.

Typical metadata includes:

| Field | Purpose |
|---|---|
| `generated_at` | Date and time when the result was generated. |
| `calculation_date` | Business date used for the calculation, when applicable. |
| `scope` | Scope of the result, such as wallet or user. |
| `wallet_id` / `user_id` | Identifier of the relevant entity. |
| `generator` | Application and version responsible for generation. |
| `sources` | References to the source data used. |
| `data_hash` | Semantic hash of normalized source data. |
| `role` | Functional role of the generated output. |

Semantic hashes are calculated from normalized data rather than from the binary representation of source files.

This makes them useful for identifying meaningful changes even when file formatting or row ordering changes.

The purpose of this traceability mechanism is to provide practical transparency without introducing a complete versioning or reproducibility framework.

## 11. Data Ownership and Persistence Rules

The following rules apply throughout Patrimonia.

1. Reference data is maintained in the shared catalogue.
2. User input files remain under user control.
3. Patrimonia never modifies original transaction or official balance workbooks.
4. Calculated data is generated from validated sources.
5. Previous calculated outputs are not treated as authoritative inputs for full recalculation workflows.
6. A calculated balance becomes an official input only through an explicit user action.
7. Asset fetching does not modify the reference catalogue; applying validated scraped data does.
8. Calculated outputs should be validated and safely persisted.

These rules establish clear ownership boundaries and prevent accidental mixing of original data and derived results.

## 12. Architectural Summary

The main Patrimonia data flows can be summarized as follows:

```text
                    REFERENCE DATA
                          |
              +-----------+-----------+
              |                       |
              v                       v
        Asset Processing        Business Rules
          Fetch / Apply                |
              |                       |
              v                       |
       Updated Catalogue              |
                                      |
                                      |
USER INPUT DATA                       |
      |                               |
      +-------------------------------+
      |
      +--> Transaction Excel
      |          |
      |          v
      |    Validation
      |          |
      |          v
      |    Full Enrichment
      |          |
      |          v
      |    Enriched Transactions (YAML)
      |          |
      |          |
      +--> Official Balance Excel
                 |
                 v
              Validation
                 |
                 +-------------------+
                                     |
                                     v
                              Balance Calculation
                                     |
                                     v
                              Calculated Balances
                                     |
                                     v
                              Portfolio Evolution
                                     |
                                     v
                                 Dashboards
                                     |
                                     v
                              HTML + Metadata
```

The architecture follows a consistent principle:

**Original data is preserved, derived data is regenerated from validated sources, and every processing stage has a clearly defined responsibility.**
