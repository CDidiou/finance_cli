# User and Wallet Data Structure

## 1. Purpose and Scope

This document describes how user-related data is organized, stored, validated, and used by Patrimonia.

It covers:

- User and wallet descriptive information.
- Original transaction and balance data.
- Validated and enriched transactions.
- Official and calculated balance snapshots.
- Data access and storage backends.
- The relationship between transaction validation and balance calculation.

The main principle is to distinguish original user-provided data from data generated by Patrimonia.

## 2. Data Organization

Patrimonia separates user data into three categories:

| Category | Purpose | Managed by |
|---|---|---|
| Descriptive data | User and wallet definitions | User / Patrimonia |
| Input data | Original transaction and official balance sources | User |
| Calculated data | Validated, enriched, and calculated results | Patrimonia |

Original user-provided data is never modified by Patrimonia.

Calculated data is derived from validated sources and can be regenerated.

### 2.1 Directory Structure

The general organization is:

```text
external-data/
└── users/
    └── <USER_ID>/
        ├── <USER_ID>.yaml
        ├── <WALLET_ID>.yaml
        ├── input/
        │   └── <WALLET_ID>/
        │       ├── transactions/
        │       │   └── ...
        │       └── balances/
        │           └── ...
        └── calculated/
            └── <WALLET_ID>/
                ├── transactions_enriched/
                │   └── ...
                └── balances/
                    └── ...
```

The exact file names, directory names, and formats are defined by the application configuration.

The directory structure distinguishes:

- Descriptive YAML files.
- Original user-provided input files.
- Results generated by Patrimonia.

## 3. Descriptive Data

### 3.1 User Definition

Each user is described by a YAML file:

```text
external-data/users/<USER_ID>.yaml
```

The user definition contains the user's descriptive information and references the wallets belonging to that user.

It does not contain transaction or balance records.

### 3.2 Wallet Definition

Each wallet is described by a separate YAML file:

```text
external-data/users/<USER_ID>/<WALLET_ID>.yaml
```

A wallet definition contains its descriptive and configuration information.

In particular, the wallet identifies its associated cash asset through `cash_asset`.

The cash asset is used to represent the cash side of transactions involving investments, sales, fees, yields, and gifts.

User and wallet definitions remain YAML files regardless of the transaction and balance storage backend.

## 4. Input Data

Input data contains the original information supplied or explicitly approved by the user.

Patrimonia reads and validates this information but does not modify the original files.

### 4.1 Transactions

Original transactions are stored under:

```text
external-data/users/<USER_ID>/input/<WALLET_ID>/transactions/
```

The source format is Excel.

A transaction source workbook contains two worksheets:

- `header`: workbook metadata.
- `data`: transaction records.

The `header` worksheet contains metadata as key/value pairs in columns A and B.

The `data` worksheet contains column names in its first row, followed by transaction records.

The transaction source contains user-entered operations only. Cash counterpart transactions are generated by the validation and enrichment process.

### 4.2 Official Balances

Official balance snapshots are stored under:

```text
external-data/users/<USER_ID>/input/<WALLET_ID>/balances/
```

The source format is Excel.

An official balance represents a reference snapshot used as the starting point for subsequent balance calculations.

It may originate from:

- A balance statement provided by a financial institution.
- A balance previously calculated by Patrimonia and explicitly copied by the user into the input directory.

The user explicitly decides when a calculated balance becomes an official input balance.

Patrimonia never promotes a calculated balance to an official balance automatically.

The balance metadata identifies its provenance, for example:

- `broker`: originating from a financial institution.
- `patrimonia`: previously calculated by Patrimonia and explicitly adopted by the user.

## 5. Calculated Data

Calculated data is generated by Patrimonia from validated input sources.

It is stored separately from original user data and can be regenerated.

### 5.1 Enriched Transactions

Enriched transactions are stored under:

```text
external-data/users/<USER_ID>/calculated/<WALLET_ID>/transactions_enriched/
```

The enriched transaction dataset is generated from the validated original transaction sources.

It contains:

- Original user-entered transactions.
- Generated cash counterpart transactions.
- Calculated PRU information.
- Transaction origin information.
- Relevant source and validation metadata.

The enriched dataset is stored in YAML.

The calculation is a full regeneration from the validated source files whenever a command requires the enriched transactions.

The previous enriched dataset is not used as the input for the next calculation.

Consequently:

- It is not an independent source of truth.
- It is not incrementally updated.
- It can be regenerated from the original sources and applicable processing rules.

The enriched transactions provide the input for wallet balance calculations.

### 5.2 Calculated Balances

Calculated balance snapshots are stored under:

```text
external-data/users/<USER_ID>/calculated/<WALLET_ID>/balances/
```

They are generated from:

- The most recent applicable official balance.
- Validated and enriched transactions after that balance date.
- Historical quotes required to value the positions.

A calculated balance is associated with a user-selected target date.

It remains a calculated result until the user explicitly copies it into the input directory to make it an official balance.

### 5.3 Data Lifecycle

The overall data flow is:

```text
User and wallet definitions
          │
          ▼
Original input data
    ├── Transactions (Excel)
    └── Official balances (Excel)
          │
          ▼
Validation and enrichment
          │
          ▼
Enriched transactions (YAML)
          │
          ▼
Balance calculation
          │
          ├── Latest applicable official balance
          ├── Enriched transactions
          └── Historical quotes
          │
          ▼
Calculated balance (Excel)
          │
          ▼
Optional user approval
          │
          ▼
New official balance (input)
```

This separation ensures that original data remains protected and calculated results can be regenerated independently.

## 6. Transaction Validation and Enrichment

### 6.1 Purpose

`TransactionValidationService` validates the original transaction sources and produces the enriched transaction dataset.

It checks the consistency of user-entered operations and generates the cash counterpart transactions required by the accounting model.

The service operates on validated source data and produces a separate calculated result.

### 6.2 Transaction Source Format

A source transaction represents one user-entered operation.

Typical actions include:

| Action | Meaning |
|---|---|
| `cash_in` | Cash contribution to the wallet |
| `cash_out` | Cash withdrawal from the wallet |
| `buy` | Purchase of an asset |
| `sell` | Sale of an asset |
| `yield` | Income generated by an asset |
| `fees` | Fees associated with an asset |
| `gift` | Asset received as a gift |

The user enters only the operation concerning the relevant asset or cash movement.

Cash counterpart transactions are generated automatically using the wallet's configured `cash_asset`.

### 6.3 Generated Cash Counterparts

The following counterpart operations are generated:

| Original operation | Generated cash operation |
|---|---|
| `buy` | `sell` cash |
| `fees` | `sell` cash |
| `sell` | `buy` cash |
| `yield` | `buy` cash |
| `gift` | `buy` cash |

External cash movements are entered explicitly:

- `cash_in` increases wallet cash.
- `cash_out` decreases wallet cash.

These operations are not paired with another transaction.

Cash counterpart transactions must be generated exactly once and associated with their original operation.

### 6.4 Validation Rules

The transaction validation process checks:

- Source workbook structure.
- Required fields and data types.
- Wallet currency consistency.
- Quantities and amounts according to the transaction action.
- Chronological ordering of source transactions.
- Consistency between asset transactions and their cash counterparts.
- Availability of sufficient quantities for sales.
- Availability of sufficient cash for withdrawals and cash expenses.
- Consistency with the previous balance when one is available.

The wallet's `cash_asset` defines the asset used for internal cash transactions.

The validator rejects source files containing manually entered internal cash counterpart transactions.

### 6.5 Cash Counterpart Validation

Generated counterpart transactions are checked to ensure that they:

- Exist exactly once for each operation requiring a counterpart.
- Reference the correct original transaction.
- Have the same transaction date.
- Have the corresponding amount.
- Respect the expected transaction order.
- Use the wallet's configured cash asset.

The validation process must distinguish generated counterpart transactions from original user-entered operations.

### 6.6 Weighted Average Cost (PRU)

The weighted average cost is calculated during transaction validation.

It is initialized from the previous balance when available.

Purchases update the weighted average cost according to the quantities and acquisition costs.

Sales:

- Reduce the remaining quantity.
- Preserve the unit PRU.
- Increase realized gains by the difference between the sale proceeds and the cost basis of the quantity sold.

The enriched transactions contain the following calculated fields:

| Field | Meaning |
|---|---|
| `pru_shares` | Remaining quantity after the transaction |
| `pru_value` | Unit PRU after the transaction |

Additional transaction effects include:

- `fees` decrease realized gains.
- `yield` increases realized gains.
- `gift` increases realized gains.
- `cash_in` and `cash_out` affect the investment amount (`invest`).

Only external cash movements modify `invest` directly.

The exact calculation formulas and accounting conventions belong to the transaction domain specification.

### 6.7 Validation Results

When validation fails:

- Validation issues identify the source workbook and relevant row.
- No new valid enriched dataset is produced.
- Original input files remain unchanged.

When validation succeeds:

- The enriched dataset is generated in YAML.
- Original transactions and generated cash counterparts are included.
- Calculated PRU fields are populated.
- Each transaction records its origin.

The origin distinguishes:

- `user`: an operation entered by the user.
- `generated_cash_counterpart`: an operation generated by Patrimonia.

Source and validation metadata should provide sufficient traceability to identify the source data and the validation run.

Hashes may be used to detect changes in source and enriched transaction content.

The source hash must be based on normalized logical user-entered data, independently of row ordering and calculated fields.

The enriched dataset hash must represent the normalized validated result, including generated counterpart transactions and calculated values.

## 7. Balance Calculation

### 7.1 Purpose

Balance calculation produces a wallet snapshot at a target date.

It starts from an official balance and applies subsequent transactions to reconstruct the wallet's positions and value.

`BalanceCalculationService` receives the required validated data explicitly.

It does not depend on the transaction storage backend.

### 7.2 Starting Balance Selection

The calling service selects the most recent official balance whose date is less than or equal to the requested target date.

This snapshot is the starting point for the calculation.

The calculation uses only transactions occurring after the starting balance date and up to the target date:

\[
\text{snapshot date} < \text{transaction date} \leq \text{target date}
\]

Transactions are therefore processed in chronological order.

### 7.3 Required Inputs

The balance calculation requires:

- A starting `BalanceSnapshot`.
- A successfully validated and enriched transaction dataset.
- A target date.
- The historical quote data required to value the relevant assets.

The service must reject invalid validation results or results for which the enriched transaction dataset is unavailable.

### 7.4 Quote Retrieval

Historical quotes are read from the configured asset quote directory.

For each asset, the calculation uses the latest available quote on or before the target date.

Assets that are explicitly configured as having a constant quote of one are valued at `1`.

If a required quote history is missing or no usable quote is available for the target date, the calculation stops with an explicit error.

The quote retrieval and selection policy must be consistent with the asset quote data conventions.

### 7.5 Calculation Output

The calculated balance is written according to the configured location:

```text
results.calculated.by_wallet.balance
```

A companion warning file may be generated alongside the balance:

```text
warning_balance_<TARGET_DATE>.yaml
```

It records, for each asset, the quote date and quote value selected during the calculation.

This provides traceability for the valuation performed at the target date.

A calculated balance remains separate from official input balances.

## 8. Excel Backend

Excel is the original input format for transaction and official balance workbooks.

The workbook naming conventions, schemas, and storage paths are defined under `data.excel` in `config/config_app.yaml`.

### 8.1 Directory Structure

```text
external-data/users/<USER_ID>/input/<WALLET_ID>/
    transactions/
    balances/
```

The exact workbook names are determined by the application configuration.

### 8.2 Workbook Structure

Each workbook must contain exactly two worksheets:

- `header`
- `data`

Worksheet names are case-sensitive.

#### Header Worksheet

Metadata names are stored in column A and their corresponding values in column B.

Required metadata fields are defined by the applicable schema.

#### Data Worksheet

The first row contains the expected column names.

The column names must match the schema exactly:

- Same names.
- Same order.
- Same capitalization.

Data records start on row 2.

### 8.3 Data Boundary

The first completely empty row marks the end of the data records.

Any non-empty data after that row invalidates the workbook.

The reader checks the underlying workbook XML to detect data beyond the first empty row without treating formatting-only rows added by Excel as data.

Total rows, subtotal rows, and comment rows are not allowed.

### 8.4 Workbook Restrictions

The following restrictions apply to the `data` worksheet:

- Merged cells are prohibited.
- Filters are prohibited.
- Excel tables are prohibited.

Each cell value must conform to the applicable schema constraints, including:

- Data type.
- Nullability.
- Minimum and maximum values.
- Allowed values.
- Date format.

Textual dates must match the exact format configured for the field. Alternative date formats are not accepted.

Allowed values are case-sensitive.

### 8.5 Reading and Validation Sequence

The reading process follows this order:

1. Workbook structure validation.
2. Cell value validation.
3. Conversion into domain objects.

A workbook is rejected if any structural or value constraint is violated.

### 8.6 Transaction Workbooks

Transaction workbooks are validated against the transaction schema, identified by `tx-schema`.

Their headers contain the required wallet and period metadata.

The data rows are converted into transaction records.

### 8.7 Balance Workbooks

Balance workbooks are validated against `balance-schema`.

Their headers identify the wallet and snapshot date.

Each data row represents a position in the snapshot.

Financial values are represented using Python `Decimal` to avoid floating-point precision loss.

## 9. Data Access and Repository Responsibilities

Data access is separated from business logic.

The domain model and calculation services must not depend directly on Excel workbook structures or SQLite tables.

The data access layer is responsible for:

- Reading source data.
- Validating storage-specific formats.
- Converting records into domain objects.
- Returning data in a consistent representation.

The storage backend must not change the business meaning of the returned transactions or balance snapshots.

Where multiple storage backends are supported, the application selects the appropriate reader through dependency injection.

The composition layer is responsible for constructing the reader according to the application configuration.

The domain model and calculation services receive their dependencies explicitly and do not instantiate storage readers themselves.

## 10. Data Integrity and Traceability

The following principles apply to all user data:

1. Original input files are never modified by Patrimonia.
2. Descriptive user and wallet definitions remain in YAML.
3. Calculated data is stored separately from original input data.
4. Enriched transactions are regenerated from validated sources.
5. Calculated balances are derived from official balances and validated transactions.
6. A calculated balance becomes official only through an explicit user action.
7. Financial amounts must preserve decimal precision.
8. Validation and calculation failures must not silently produce incomplete or misleading results.
9. Source and calculation metadata should provide sufficient traceability without introducing unnecessary reproducibility infrastructure.

## Appendix A — SQLite Backend

This appendix documents the SQLite storage option and its technical representation.

SQLite is an alternative storage backend for transaction and balance records. It does not replace the YAML definitions of users and wallets.

### A.1 Configuration

The SQLite database path is configured through `data.sqlite.path`.

A relative path is resolved from the project root.

The database contains transaction and balance-position records only. User and wallet descriptive information remains stored in YAML.

### A.2 Reader Interface

The storage reader abstraction exposes the following operations:

```python
read_transactions(
    user_id,
    wallet_id,
    start_date=None,
    end_date=None,
)

read_balances(user_id, wallet_id)
```

The transaction reader returns transactions ordered by date.

When a date range is provided, the filtering convention is:

\[
\text{start date} < \text{transaction date} \leq \text{end date}
\]

The balance reader returns snapshots ordered by date.

Each snapshot consists of:

- Snapshot date.
- Wallet identifier.
- Associated positions.

The same business-level interface is intended to be used regardless of the underlying storage format.

### A.3 Database Schema

The SQLite reader expects the following tables:

```sql
CREATE TABLE wallet_transactions (
    id INTEGER PRIMARY KEY,
    user_id TEXT NOT NULL,
    wallet_id TEXT NOT NULL,
    date TEXT NOT NULL,
    action TEXT NOT NULL,
    mnemonic TEXT NOT NULL,
    name TEXT NOT NULL,
    qty TEXT,
    quote TEXT,
    value TEXT,
    pru_shares TEXT,
    pru_value TEXT
);

CREATE INDEX idx_wallet_transactions_owner_date
    ON wallet_transactions (user_id, wallet_id, date);

CREATE TABLE wallet_balance_positions (
    id INTEGER PRIMARY KEY,
    user_id TEXT NOT NULL,
    wallet_id TEXT NOT NULL,
    date TEXT NOT NULL,
    asset TEXT NOT NULL,
    name TEXT,
    invest TEXT,
    current_value TEXT,
    unrealized_gain TEXT,
    realized_gain TEXT,
    qty TEXT,
    pru TEXT,
    quote TEXT,
    asset_weight TEXT
);

CREATE INDEX idx_wallet_balance_owner_date
    ON wallet_balance_positions (user_id, wallet_id, date);
```

### A.4 Storage Conventions

Financial amounts are stored as `TEXT` to preserve decimal precision.

Dates are stored as ISO-formatted strings:

```text
YYYY-MM-DD
```

Each row in `wallet_balance_positions` represents one position in a balance snapshot.

Rows sharing the same:

- `user_id`
- `wallet_id`
- `date`

belong to the same snapshot.

### A.5 Database Lifecycle

The SQLite reader is read-only from the application's perspective.

It does not:

- Create the database.
- Create or modify tables.
- Import Excel data.
- Migrate Excel data into SQLite.
- Write calculated results into the database.

The database must already exist and contain the expected tables.

A missing database, missing table, or incompatible schema must produce an explicit error.

### A.6 Current Support Limitations

The availability of the SQLite reader does not imply that all application workflows support SQLite.

In particular, transaction validation and balance calculation must be considered separately from the generic read interface.

The currently supported command workflows and their backend limitations must be documented in the CLI reference.

No Excel-to-SQLite import or migration workflow is currently part of the documented scope.
